CareLink Backend Schema

The PostgreSQL data model: enumerations, seventeen tables, their relationships, the constraints that protect a booking's terms, the row-level policies that protect a child's record, and the views the agency's dashboard reads.

1 · Conventions

Every table has a uuid primary key defaulting to gen_random_uuid(), and created_at and updated_at as timestamptz defaulting to now(). Foreign keys are named <entity>_id. Money is stored as integer in pesewas — never a floating-point type — and every amount column is accompanied by the currency GHS implicitly. Times are timestamptz stored in UTC. Soft deletion is used only where a record is evidence: deleted_at on reviews and messages; everything else is deleted for real or cascaded.

Text that a user typed is text, never varchar(n). Enumerations are Postgres enum types, so an impossible state cannot be written even by a mistaken query. Every table has row-level security enabled with no default-permit policy.

users 1 — 0..1 staff_profiles 1 — 0..n staff_skills, staff_areas, availability_windows, availability_exceptions, certifications

The shape of the model follows one decision: a booking is the transaction record, and payments, messages, reviews, reports and state history all hang from it. Nothing about an agreed arrangement lives anywhere else, which is what makes the booking the artefact the agency can rely on in a dispute.

Constraints. An exclusion constraint prevents two bookings for the same caregiver with overlapping [starts_at, ends_at) in accepted, paid or active. A trigger refuses any change to starts_at, ends_at, hourly_rate, total_amount or address once terms_locked_at is set. Indexes on (staff_profile_id, starts_at), (parent_profile_id, created_at) and (status, starts_at).

5 · Row-level security

TablePolicy in words
usersA user reads and updates their own row, except role and account_status. An administrator reads all and updates status. No one reads another user's row directly — public caregiver data is exposed through a view
parent_profilesOwner full access. A caregiver reads the area and household notes only through a booking they hold. Administrator reads all
wardsOwner full access. A caregiver reads a ward only where a booking joins that ward to them and its status is accepted, paid, active or completed. Administrator reads only through an open report on that booking
staff_profiles and childrenOwner full access. Any authenticated user reads verified, accepting profiles through the public search view. Administrator full access
verification_submissionsOwner reads and inserts their own; only an administrator updates status, reviewer and reason. Nobody deletes
bookingsRead where the requesting user is the parent or the caregiver on the booking, or an administrator. Insert only by a verified parent. Update only through the transition function
emergency contactsNot a table but a policy: contact columns are returned to a counterparty only where a booking between them is active — the reveal window is enforced in the database, not by hiding a field in the interface
payments, messages, reviewsVisible to the two parties on the booking and to an administrator; insert restricted to the party entitled to act
reportsReporter reads their own; the subject never reads a report against them; administrators read and resolve all
booking_events, audit_logInsert by the service role; read by the booking's parties (events) or administrators only (audit); no update, no delete

Every policy ships with a negative integration test asserting that the request which should be refused is refused. A table without a policy and its negative test is not considered complete.

7 · Seed and migration notes

Migrations are numbered SQL files in the repository, forward-only, each with its policies and indexes in the same file as its table — a table and its protection are never separated across migrations. The seed script creates one administrator, twelve caregivers across four areas with varied rates, skills and availability, six parents with nine wards, and forty bookings distributed across every status including two disputes, so every screen and every dashboard figure has something real to display from the first run. Seed data is clearly marked and never mixed into production tables.
