CareLink Technical Design Document

The technology stack, architecture, integrations and the reasoning behind each choice — written so a second developer could pick the project up from this document alone.

1 · Design principles

Five principles decide the arguments that follow, in this order.

  1. One developer, five weeks. Every choice favours a stack where the same language and the same repository cover the interface, the API and the data access. Operational surface is a cost, not a feature.
  2. The database enforces the rules. Authorisation lives with the data, not only in the interface. If a route is forgotten, the row-level policy still refuses.
  3. External services are replaceable. Payments and AI sit behind internal interfaces with a fake implementation used in development, so a simulated Mobile Money flow can become a real one without touching booking logic.
  4. AI output is untrusted input. Model responses are parsed against a schema and rejected if they do not fit. No model output ever reaches the database or the query builder unvalidated.
  5. Mobile-first, low-bandwidth. Server-rendered pages, small payloads, images resized on upload. The system must be usable on a mid-range Android phone on a weak connection.

3 · Architecture

Three tiers plus an isolated integration layer. Nothing in the client talks to an external provider directly, and nothing outside the service layer writes to the database.

Client layer
Responsive React interfaces for the three roles. Server components render lists and detail pages; client components own the camera, the speech APIs, messaging and forms. No secret keys, no direct database access.
Application layer
Next.js route handlers and server actions holding all business logic: authentication guards, the booking state machine, the matching algorithm, payment orchestration and AI calls. Every entry point validates its payload and re-checks role and ownership.
Data layer
PostgreSQL with row-level security on every table, enums for the state machines, and views for the dashboard aggregates. Private storage buckets for documents and selfies.
Integration layer
Three adapters — PaymentProvider, SearchParser, PhotoPlausibilityChecker — each an interface with a real and a fake implementation, selected by environment. All secrets are server-side only.

4 · The booking state machine

Booking status is a Postgres enum and every transition passes through one function. Illegal transitions are rejected in both the service layer and a database check, because a booking's state is what the agency will rely on in a dispute.

5 · The matching algorithm

Matching runs in two passes. A hard filter in SQL removes anyone who cannot do the job: not verified, not serving the area, unavailable in the window, or already booked. A soft score then ranks the survivors on five weighted factors — availability fit 30, area proximity 25, skill match 20, rating and experience 15, budget fit 10 — each normalised to zero-to-one and multiplied by its weight, summing to a score out of 100.

Two decisions matter. Weights are read from a configuration table, not hard-coded, so the agency can retune them and the evaluation can compare rankings under different weightings. And each factor's contribution is returned alongside the total, so the parent sees the same numbers that produced the order — the transparency requirement is a data-shape decision, not a copywriting one.

New caregivers are protected from a cold-start penalty: fewer than three reviews scores at the roster median rather than zero, so a new staff member is not permanently unrankable. The scoring function is pure and unit-tested against fixture rosters, which is how ranking regressions get caught.

6 · AI integration

6.1 Natural-language search parsing

The parent's sentence is sent to the model with a system prompt describing exactly the available filter fields — area, date, start and end time, maximum hourly rate, skill tags from the fixed vocabulary, minimum experience, minimum rating — and an instruction to return JSON only, omitting anything not stated. The response is parsed against the filter schema; unknown fields are dropped, out-of-range values are dropped, and a failure falls back to the manual filter panel. The parsed filters are shown to the parent as editable chips before the search runs, so the model proposes and the parent confirms.

6.2 Photo plausibility check

A server route receives the ID photograph and the captured selfie, both already resized, and asks the vision model for one of three verdicts with a one-sentence rationale. The response is constrained to that enum; anything else is stored as uncertain. The verdict, the rationale and the model version are stored on the verification record so the evaluation can compare them against the administrator's independent decision. Nothing is auto-approved on this basis, and the check is optional and skippable.

Failure and cost handling. Both integrations run server-side with a timeout, one retry, and a per-account rate limit. If the provider is unavailable, the feature is hidden with a plain message rather than surfacing an error — neither AI feature is on the critical path to a booking.

7 · Payment integration

A payment is a record, not a redirect. The service creates a payment row in initiated against the booking, calls the provider adapter with network, phone number and amount, and updates the row on the response. The simulated provider models each real outcome, including a pending state that resolves on a delay and a timeout that leaves the row recoverable, so the interface is built against realistic behaviour. The adapter interface — initiate, poll status, refund — is deliberately the shape a live aggregator exposes.

Amounts are stored in minor units as integers, never floats. The commission split is computed at completion from a configured rate and stored on the payment, so a later rate change does not rewrite history. Every payment record keeps the provider reference visible to both parties, which is the artefact that replaces a cash handover.

9 · Environments, testing and deployment

Three environments: local development against a Supabase project seeded with mock data and both fake adapters; a preview deployment per branch on Vercel for supervisor and agency review; and production on Vercel with the same simulated payment adapter, since no live money moves in this phase.

The test pyramid follows the risk. Unit tests cover the scoring function, the state machine, the commission split and every schema. Integration tests cover the API routes, row-level policies — including negative cases, where a request that should be refused is asserted to be refused — and the payment adapter's outcomes. End-to-end tests cover three journeys: staff onboarding through verification, parent search through payment and completion, and administrator verification and report resolution. AI features are evaluated separately against a labelled sample rather than asserted in tests.

Performance is measured with Lighthouse on the parent search and administrator dashboard screens; images are resized on upload and served in a modern format; dashboard aggregates come from database views rather than client-side computation over full tables.
