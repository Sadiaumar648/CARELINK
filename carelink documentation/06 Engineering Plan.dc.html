CareLink Engineering Plan

Forty-one tasks in build order, each small enough to finish and test in a sitting, each with its dependencies and the criteria that decide whether it is done.

1 · How this plan works

Five sprints of one week, following the four phases in the proposal, with the fifth week reserved for evaluation and submission. Tasks are numbered by sprint. A task is done only when its acceptance criteria pass, its tests are written, and it is merged to the trunk — not when the code compiles.

Three standing rules. Every table arrives with its row-level policy and a negative test in the same task, so authorisation is never a later pass. Every external provider arrives behind an interface with a fake implementation, so nothing downstream waits on a credential. And the order is chosen so that something demonstrable exists at the end of every week — the risk being managed here is a compressed timeline, and the mitigation is that the project is always submittable.

7 · Critical path and what gets cut

The critical path runs 1.1 → 1.4 → 1.5 → 1.6 → 2.10 → 2.11 → 2.12 → 3.7 → 3.8 → 5.1. Everything on it is a P0 in the PRD, and nothing on it may be deferred. Slipping a task here slips the demonstration; slipping anything else does not.

If the timeline compresses further, work is cut in this order — and test coverage is never the first thing cut, because a plausible-looking system that fails during evaluation is worse than a smaller one that holds: 4.13 notifications; 4.12 settings interface, with weights left in seeded configuration; 4.7 messaging, since a phone call remains available; 4.4 natural-language search, leaving manual filters, which are the tested fallback anyway; 4.2 the photo check, leaving verification document-only. Each cut removes a whole feature cleanly rather than half-finishing several, and each is recorded in the report as a scope decision with its reason.

8 · Definition of done

A task is done when: the acceptance criteria pass on a preview deployment, not only locally; unit tests cover its logic and integration tests cover its policies including at least one refusal case; the interface matches the Design Brief at 320px and at desktop width; keyboard operation and focus states work; errors are handled inline without losing entered data; nothing is logged that should not be; and the work is merged with a message that explains why, not only what.

Weekly, three questions decide whether the plan is still true: is the week's demonstrable outcome demonstrable, is the critical path still on schedule, and has anything been learned that changes a later task. The answers go into the project log, which is itself a deliverable.
